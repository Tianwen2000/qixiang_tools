# 工具站后续项目扩展研究文档

## 1. 背景

当前工具站中的工具分类、工具排序、工具标题、副标题、标签、简要文案、详细说明等内容，主要依赖前端或后端固定配置。  
这种方式在早期开发阶段简单直接，但随着工具数量增加、后台管理需求变多，会逐渐出现以下问题：

- 修改工具展示文案需要改代码、重新构建前端、重新发版。
- 简单文案调整也要走部署流程，效率较低。
- 如果配置放在后端 JSON 文件中，多人同时登录后台修改并保存时，容易出现覆盖冲突。
- 工具配置缺少版本记录，后续不方便回滚、审计和导出。
- 用户访问量上来后，每次都读取数据库配置会增加 MySQL 压力。
- 用户反馈目前只保存在后台，后续希望可以同步到 QQ 群、钉钉群等即时通知渠道。

因此，后续可以研究把工具站展示配置做成“后端可配置 + 数据库存储 + Redis 缓存 + 后台管理 + 导出备份”的完整方案。

---

## 2. 建设目标

### 2.1 核心目标

把工具站前台展示相关配置从“前端写死”逐步改造成“后台可配置”，实现：

- 不改前端代码即可调整工具分类和工具展示内容。
- 不需要重新构建前端即可更新工具文案。
- 后台管理系统可以维护工具分类、工具排序、工具标题、副标题、标签、简要文案、详细说明。
- 配置保存到数据库，避免多人同时修改 JSON 文件造成冲突。
- 前台读取配置时优先走 Redis 缓存，减轻 MySQL 读取压力。
- 后台支持“最新配置导出”按钮，方便备份和迁移。
- 后续扩展数据分析可视化和用户反馈群通知能力。

### 2.2 非目标

第一阶段不建议一次性做太复杂，例如：

- 不急着做完整 CMS 系统。
- 不急着做复杂权限审批流。
- 不急着做多语言配置。
- 不急着做复杂 BI 数据平台。
- 不急着支持多人实时协同编辑。

建议先完成“可配置、可缓存、可导出、可回滚”的基础能力。

## 3. 整体架构设想

```text
前台用户
  ↓
前端页面请求工具配置接口
  ↓
后端接口 /api/tool-config/latest
  ↓
优先读取 Redis 缓存
  ↓
缓存命中：直接返回配置
缓存未命中：读取 MySQL 最新发布配置
  ↓
后端把最新配置写入 Redis，设置 1 小时过期
  ↓
返回给前端展示
```

后台管理流程：

```text
管理员登录后台
  ↓
进入工具配置管理页面
  ↓
编辑分类、排序、标题、副标题、标签、文案、详细说明
  ↓
保存草稿 / 发布配置
  ↓
写入 MySQL
  ↓
主动删除或更新 Redis 缓存
  ↓
前台用户读取到最新发布配置
```

## 4. 为什么不用后端 JSON 文件存配置

后端 JSON 文件适合小项目早期使用，但后续存在明显问题：

1. **多人修改冲突**  
   如果两个管理员同时打开后台并修改配置，最终保存的人可能会覆盖前一个人的修改。

2. **缺少版本管理**  
   JSON 文件本身不容易记录是谁改的、什么时候改的、改了什么。

3. **不适合做后台管理**  
   后台保存 JSON 文件需要考虑文件锁、权限、并发写入、备份恢复等问题，复杂度会越来越高。

4. **不利于扩展**  
   后续如果想做配置发布、历史版本、回滚、操作日志、数据分析，数据库更合适。

因此更建议把工具配置放到 MySQL 表中，由后台管理系统进行维护。

## 5. 数据库存储设计思路

### 5.1 工具分类表：tool_categories

用于维护工具大类。

建议字段：

```text
id              主键
category_key    分类唯一标识，例如 text_tools、image_tools
title           分类标题
subtitle        分类副标题
description     分类说明
sort_order      分类排序
is_enabled      是否启用
created_at      创建时间
updated_at      更新时间
```

### 5.2 工具配置表：tool_items

用于维护每个工具的展示信息。

建议字段：

```text
id                  主键
tool_key            工具唯一标识，例如 unicode_converter
category_id         所属分类 ID
title               工具标题
subtitle            工具副标题
tags                标签，可以用 JSON 字段存数组
summary             简要文案
description         详细说明
route_path          前端路由地址
icon                图标标识或图标地址
sort_order          工具排序
is_enabled          是否启用
created_at          创建时间
updated_at          更新时间
```

### 5.3 配置版本表：tool_config_versions

用于保存每次发布后的完整配置快照，方便导出、回滚和审计。

建议字段：

```text
id                  主键
version_no          版本号，例如 20260626-001
config_json         完整配置 JSON 快照
status              状态：draft / published / archived
created_by          创建人
published_by        发布人
created_at          创建时间
published_at        发布时间
remark              发布备注
```

### 5.4 操作日志表：admin_operation_logs

用于记录后台配置修改行为。

建议字段：

```text
id                  主键
admin_account       管理员账号
action              操作类型，例如 create、update、publish、export
target_type         操作对象类型
target_id           操作对象 ID
detail              操作详情 JSON
ip                  操作 IP
user_agent          UA
created_at          操作时间
```

## 6. 并发修改处理

为了避免多人同时修改配置导致互相覆盖，可以研究以下方案。

### 6.1 乐观锁

每条配置记录增加一个版本字段：

```text
version
```

管理员打开编辑页面时读取当前版本号。  
保存时后端检查版本号是否一致：

```text
如果版本号一致：允许保存，并把 version + 1
如果版本号不一致：拒绝保存，提示“配置已被其他管理员修改，请刷新后再编辑”
```

这种方式简单，适合当前项目。

### 6.2 草稿和发布分离

可以把后台编辑分成两个动作：

```text
保存草稿
发布配置
```

好处：

- 草稿可以多次修改，不影响前台展示。
- 只有点击“发布”后，前台才读取新配置。
- 发布时生成一份完整配置快照，方便导出和回滚。

### 6.3 发布前二次确认

发布按钮可以加确认弹窗：

```text
确认发布当前工具站配置吗？
发布后前台用户将看到最新配置。
```

这样可以减少误操作。

## 7. Redis 缓存设计

### 7.1 缓存目标

前台工具站访问量可能比较大，但工具配置变化频率不高。  
因此适合用 Redis 缓存最新配置，减少 MySQL 读取压力。

### 7.2 推荐缓存模式：Cache Aside

前台读取配置时：

```text
1. 后端先查 Redis
2. Redis 有数据，直接返回
3. Redis 没数据，查 MySQL 最新发布配置
4. 后端把 MySQL 结果写入 Redis
5. Redis 设置 1 小时过期
6. 返回配置给前端
```

### 7.3 Redis Key 设计

建议：

```text
tool_config:latest
```

如果后续支持多环境或多站点，可以扩展为：

```text
tool_config:{site}:latest
tool_config:{env}:latest
```

例如：

```text
tool_config:qixiang:prod:latest
```

### 7.4 过期时间

建议第一阶段设置：

```text
TTL = 1 小时
```

也就是：

```text
3600 秒
```

用户设想中的“一万个用户中只要有一个用户打开工具站并拉到最新配置，就把配置更新到 Redis，其他用户后续从 Redis 拉”，本质就是缓存预热或被动填充缓存。

### 7.5 发布配置后的缓存处理

后台发布新配置后，不建议等 Redis 自然过期。  
更推荐发布成功后主动处理缓存：

```text
方案 A：删除 Redis 旧缓存
方案 B：直接把最新配置写入 Redis
```

更推荐方案 B：

```text
发布配置成功
  ↓
生成最新 config_json
  ↓
写入 MySQL 版本表
  ↓
更新 Redis tool_config:latest
  ↓
设置 TTL 1 小时
```

这样前台几乎可以马上看到新配置。

### 7.6 缓存击穿防护

如果 Redis 刚好过期，同时大量用户访问，可能会一起打到 MySQL。  
后续可以研究：

- 给读取数据库加短暂分布式锁。
- 缓存空值或默认配置。
- 发布后主动刷新 Redis，减少自然过期时的瞬间压力。

第一阶段可以先不做太复杂，只要配置数据量不大，问题不会很明显。

## 8. 后端接口设计草案

### 8.1 前台读取最新配置

```http
GET /api/tool-config/latest
```

返回示例：

```json
{
  "code": 0,
  "data": {
    "version": "20260626-001",
    "categories": [
      {
        "key": "text_tools",
        "title": "文本工具",
        "subtitle": "常用文本处理能力",
        "sort_order": 1,
        "tools": [
          {
            "key": "unicode_converter",
            "title": "Unicode 转换",
            "subtitle": "字符、码点、转义互转",
            "tags": ["Unicode", "编码", "开发"],
            "summary": "快速完成 Unicode 编码转换。",
            "description": "支持字符转 Unicode 码点、Unicode 转义等常见开发场景。",
            "route_path": "/tools/unicode-converter",
            "sort_order": 1
          }
        ]
      }
    ]
  }
}
```

### 8.2 后台读取配置列表

```http
GET /api/backoffice/tool-config
```

### 8.3 后台保存分类

```http
POST /api/backoffice/tool-categories
PUT /api/backoffice/tool-categories/{id}
```

### 8.4 后台保存工具

```http
POST /api/backoffice/tool-items
PUT /api/backoffice/tool-items/{id}
```

### 8.5 后台发布配置

```http
POST /api/backoffice/tool-config/publish
```

发布时：

```text
1. 校验当前配置合法性
2. 生成完整 config_json
3. 写入版本表
4. 更新 Redis 最新缓存
5. 记录后台操作日志
```

### 8.6 后台导出最新配置

```http
GET /api/backoffice/tool-config/export
```

导出内容可以是：

```text
tool-config-latest-版本号.json
```

或者：

```text
tool-config-latest-版本号.md
```

第一阶段建议导出 JSON，方便备份和迁移。

## 10. 前端改造思路

### 10.1 当前问题

如果工具展示内容写死在前端代码中，那么每次修改标题、标签、排序都需要：

```text
改前端代码
  ↓
npm run build
  ↓
同步 dist
  ↓
刷新线上页面
```

这对简单文案调整来说太重。

### 10.2 改造目标

前端启动时或页面加载时请求后端配置接口：

```text
GET /api/tool-config/latest
```

然后根据返回数据渲染工具分类和工具卡片。

### 10.3 前端保留内容

前端仍然保留：

- 工具实际功能页面
- 工具路由
- 工具组件
- 基础布局
- 交互逻辑

后端配置主要控制：

- 分类显示与排序
- 工具是否展示
- 工具标题
- 工具副标题
- 工具标签
- 工具简介
- 工具详细说明
- 工具入口路径

也就是说：

```text
功能代码仍然在前端
展示配置由后台控制
```

这样既能保证安全稳定，也能减少发版次数。

## 11. 数据分析可视化方向

后续后台可以继续增加管理和数据分析功能。

### 11.1 用户访问统计

可以统计：

- 今日访问量
- 近 7 日访问趋势
- 近 30 日访问趋势
- 工具访问排行
- 来源页面统计
- 设备类型统计
- 浏览器统计
- IP 地区统计

### 11.2 工具使用分析

可以统计：

- 哪些工具使用最多
- 哪些工具打开后没有执行操作
- 每个工具的执行次数
- 每个工具的失败率
- 每个工具的平均处理耗时

### 11.3 用户反馈分析

可以统计：

- 反馈总数
- 今日新增反馈
- 反馈类型分布
- 反馈所属工具排行
- 未处理反馈数量
- 高频问题关键词

### 11.4 可视化展示形式

可以在后台加入：

- 折线图：访问趋势
- 柱状图：工具使用排行
- 饼图：反馈类型分布
- 表格：最近反馈、最近登录、最近错误
- 卡片：今日访问、今日反馈、工具数量、异常数量

## 12. 用户反馈同步到 QQ 群 / 钉钉群研究

### 12.1 目标

当用户提交反馈后，除了写入数据库，也可以同步通知到群里，方便及时处理。

例如：

```text
用户提交反馈
  ↓
后端写入 feedback 表
  ↓
后端调用群机器人 webhook
  ↓
QQ 群 / 钉钉群收到通知
```

### 12.2 钉钉群机器人

钉钉通常支持自定义机器人 webhook。  
后端可以发送 HTTP POST 请求，把反馈内容推送到群里。

通知内容示例：

```text
【工具站新反馈】
类型：问题反馈
工具：Unicode 转换
账号：15573808035
内容：移动端按钮显示异常
联系方式：QQ：123456
来源页：/tools/unicode-converter
时间：2026-06-26 10:30:00
```

### 12.3 QQ 群机器人

QQ 群同步需要根据后续选型研究：

- QQ 官方机器人能力
- 第三方机器人框架
- 企业微信 / 钉钉替代方案
- 是否需要服务器常驻机器人进程
- 是否存在账号风控和稳定性问题

第一阶段更建议优先研究钉钉或企业微信 webhook，因为实现更标准、稳定性更好。

### 12.4 失败处理

群通知不能影响用户反馈提交成功。  
推荐流程：

```text
1. 反馈先入库
2. 入库成功后异步发送群通知
3. 群通知失败只记录日志，不影响用户提交结果
```

后续可以加入：

- 通知失败重试
- 通知开关
- 通知模板配置
- 只推送 bug 类型反馈
- 按工具分类推送到不同群

## 13. 推荐实施阶段

目标：

- 建表：工具分类表、工具配置表、配置版本表
- 后台支持编辑分类和工具展示信息
- 前台通过接口读取配置
- 支持排序、标题、副标题、标签、简要文案、详细说明

交付结果：

- 简单配置不再需要前端发版
- 工具展示内容可在后台调整

### 第二阶段：发布和导出

目标：

- 支持保存草稿
- 支持发布配置
- 发布后生成版本快照
- 后台增加“导出最新配置”按钮
- 支持历史版本查看

交付结果：

- 配置可审计
- 配置可备份
- 配置可回滚

### 第三阶段：Redis 缓存

目标：

- 前台最新配置接口优先读取 Redis
- Redis 未命中再读取 MySQL
- 缓存 TTL 设置为 1 小时
- 后台发布配置后主动更新 Redis

交付结果：

- 减少 MySQL 读取压力
- 提高前台配置接口响应速度

目标：

- 统计访问量、工具使用量、反馈数量

交付结果：

### 第五阶段：反馈群通知

目标：

- 用户提交反馈后同步到钉钉群或 QQ 群
- 支持通知开关
- 支持通知模板
- 支持通知失败日志

交付结果：

- 反馈处理更及时
- 管理员不用频繁打开后台查看新反馈

## 14. 风险和注意点

### 14.1 配置不要控制过多功能逻辑

后台配置适合控制展示信息，不建议直接控制复杂业务逻辑。  
否则可能出现后台误配置导致前台功能异常。

建议边界：

```text
后台配置：标题、文案、标签、排序、是否展示
前端代码：实际工具功能、核心交互、路由组件
```

### 14.2 配置发布前必须校验

发布前要检查：

- 分类 key 是否重复
- 工具 key 是否重复
- 标题是否为空
- route_path 是否存在
- 排序值是否合法
- 标签格式是否正确
- 禁用分类下是否还有启用工具

### 14.3 Redis 不能当唯一数据源

Redis 是缓存，不是主数据源。  
主数据仍然应该保存在 MySQL 中。

### 14.4 导出配置不能包含敏感信息

导出的最新配置只应该包含前台展示配置。  
不要包含：

- 管理员账号密码
- token
- secret key
- 数据库连接
- 内部接口密钥

### 14.5 群机器人密钥要放环境变量

钉钉 / QQ / 企业微信 webhook 地址可能包含密钥。  
不要写死在代码里，不要提交 Git。  
建议放到服务器环境变量或后台安全配置中。

## 15. 初步优先级建议

建议优先级如下：

```text
P0：工具配置数据库化
P0：后台编辑工具分类和工具信息
P0：前台读取后端最新配置
P1：配置发布版本和最新配置导出
P1：Redis 缓存最新配置
P2：历史版本回滚
P2：后台数据统计卡片
P2：反馈同步到钉钉群
P3：QQ 群机器人研究
P3：更完整的数据分析可视化
```

## 16. 总结

后续工具站扩展可以围绕一个核心方向推进：

```text
把展示配置从代码中抽离出来
  ↓
放入数据库统一管理
  ↓
后台可编辑、可发布、可导出
  ↓
前台通过接口读取
  ↓
Redis 缓存减轻数据库压力
  ↓
逐步增加数据分析和即时反馈通知
```

这样做的好处是：

- 简单文案和排序调整不需要前端重新发版。
- 多人后台修改不会像 JSON 文件那样容易互相覆盖。
- 配置有版本、有记录、可导出、可回滚。
- Redis 可以减少 MySQL 压力，提高访问速度。
- 后台后续可以继续扩展成运营管理和数据分析平台。
- 用户反馈可以更及时同步给管理员处理。
